# [첨부 1] 3노드 24-GPU 클러스터링 기술검토 및 개선사항

대상 시스템: master / n1 / n3 (노드당 GPU 8기, 총 24기)
목표 상태: 3노드 24-GPU를 단일 분산학습 잡으로 운용 (NCCL 기반 데이터/텐서/파이프라인 병렬)
현재 상태: 노드 내 8-GPU 단일 노드 학습만 동작, 노드 간 결합 실패

---

## 1. 문제 정의

`8 GPU × 3 node = 24 GPU` 구성이 물리적으로는 존재하나, 논리적으로 하나의 학습 잡을 형성하지 못합니다.
증상은 통상 다음 중 하나로 나타납니다.

| 증상 유형 | 관측 형태 | 통상 원인 계층 |
|---|---|---|
| A. 랑데부 실패 | `torchrun`이 rank 등록 단계에서 무한 대기 후 타임아웃 | 네트워크 도달성 / 포트 / 호스트명 해석 |
| B. NCCL 초기화 실패 | `NCCL WARN ... unhandled system error`, `Bootstrap : no socket interface found` | NCCL 인터페이스 선택 (`NCCL_SOCKET_IFNAME`) |
| C. 초기화는 되나 극도로 느림 | all_reduce 대역폭이 노드 내 대비 1/10 이하, step time 급증 | 인터커넥트가 TCP 소켓 폴백 (RDMA 미사용) |
| D. 학습 중 산발적 hang | 수십~수백 step 후 멈춤, `Watchdog caught collective timeout` | MTU/PMTU, 방화벽, ACS, 드라이버 버전 불일치 |
| E. 버전 불일치 오류 | `NCCL version mismatch`, CUDA 오류 | 노드 간 드라이버/CUDA/NCCL/프레임워크 버전 상이 |

> **본 시스템의 실제 증상 유형: ( ○ ) — 진단 스크립트 실행 후 기재**

## 2. 근본원인 후보 및 점검 항목

### 2-1. [최우선] 노드 간 인터커넥트 — RDMA 가용 여부

**가장 흔하고, 가장 영향이 큰 원인입니다.**

멀티노드 학습의 all-reduce 트래픽은 InfiniBand 또는 RoCE(RDMA over Converged Ethernet) 없이는 실용적인 속도가 나오지 않습니다. 일반 1GbE/10GbE TCP 소켓으로 폴백되면 24-GPU 학습이 8-GPU 학습보다 **오히려 느려지는** 역전 현상이 발생하며, 이 경우 운영자는 멀티노드 사용을 포기하게 되어 **GPU Utilization 저하의 직접 원인**이 됩니다.

점검:

```bash
# IB 장치 존재 여부
ibstat; ibv_devinfo; ibdev2netdev

# 링크 상태 및 속도
ibstatus | grep -E "state|rate"

# 노드 간 실제 대역폭 (n1에서 서버, master에서 클라이언트)
ib_write_bw            # n1
ib_write_bw <n1_ip>    # master

# RDMA가 없다면 이더넷 실측
iperf3 -s              # n1
iperf3 -c <n1_ip> -P 8 # master
```

판정 기준:

| 실측 노드 간 대역폭 | 판정 | 조치 |
|---|---|---|
| 100 Gbps 이상 (IB/RoCE) | 정상 | NCCL 튜닝만 수행 |
| 10~25 Gbps (이더넷) | 제한적 | 통신량 적은 병렬 전략으로 우회 (§4) |
| 1 Gbps 이하 | **멀티노드 학습 불가** | 인터커넥트 증설 필요 → 운영기관 협의 대상 |

### 2-2. NCCL 통신 인터페이스 선택 오류

노드에 관리용 NIC, 도커 브리지(`docker0`), 가상 인터페이스가 여러 개 있으면 NCCL이 잘못된 인터페이스를 선택해 랑데부에 실패하거나 관리망(저속)으로 트래픽을 흘립니다.

```bash
# 각 노드에서 인터페이스 확인
ip -br addr

# 학습 실행 시 명시적으로 지정 (예: 데이터망이 enp1s0f0인 경우)
export NCCL_SOCKET_IFNAME=enp1s0f0     # 또는 IB 사용 시 ib0
export NCCL_IB_HCA=mlx5_0,mlx5_1
export NCCL_IB_DISABLE=0                # RDMA 사용 (0), 미사용 시 1
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH
```

`NCCL_DEBUG=INFO` 로그에서 `NET/IB` 가 아닌 `NET/Socket` 으로 표시되면 RDMA가 적용되지 않은 상태입니다.

### 2-3. 노드 간 소프트웨어 버전 불일치

3노드의 드라이버/CUDA/NCCL/PyTorch 버전이 하나라도 다르면 집합통신이 실패하거나 비결정적으로 hang 됩니다.

```bash
for h in master n1 n3; do
  echo "=== $h ==="
  ssh $h 'nvidia-smi --query-gpu=driver_version,name --format=csv,noheader | head -1;
          nvcc --version | grep release;
          python -c "import torch;print(torch.__version__, torch.cuda.nccl.version())"'
done
```

→ **3노드 출력이 완전히 동일해야 합니다.**

### 2-4. 방화벽 / 포트 / 호스트명 해석

- `torchrun` 랑데부 포트(기본 29500)와 NCCL이 동적 할당하는 포트 대역이 노드 간 전 구간 개방되어야 합니다.
- 각 노드가 서로의 호스트명(`master`, `n1`, `n3`)을 해석할 수 있어야 합니다(`/etc/hosts` 또는 DNS).
- 컨테이너 사용 시 `--network=host --ipc=host --ulimit memlock=-1 --ulimit stack=67108864` 및 `--device=/dev/infiniband` 필요.

```bash
for h in master n1 n3; do ssh $h 'systemctl is-active firewalld ufw 2>/dev/null; getent hosts master n1 n3'; done
```

### 2-5. 공유 스토리지 부재

멀티노드 학습은 모든 노드가 **동일 경로**에서 데이터셋·체크포인트에 접근해야 합니다. 공유 파일시스템이 없으면 각 노드 로컬 복제가 필요해 운영 부담과 GPU 유휴가 발생합니다.

### 2-6. 노드 결번(n2 부재) 관련

노드 이름이 `master, n1, n3`로 **n2가 결번**입니다. 이것이 단순 명명 규칙이라면 문제없으나, 아래에 해당하면 확인이 필요합니다.

- 원래 4노드(32-GPU) 구성에서 n2가 **장애·반납·미납품** 상태인 경우 → 자원 현황 자체를 운영기관과 재확인해야 합니다.
- 호스트 목록/스케줄러 설정 파일에 n2가 남아 있는 경우 → 랑데부 시 존재하지 않는 노드를 기다리다 **타임아웃**이 발생하므로, 설정에서 제거해야 합니다.

```bash
grep -rn "n2" /etc/hosts /etc/slurm/ ~/.ssh/config 2>/dev/null
```

> **확인 필요 사항: n2 노드의 존재 여부 및 상태 → ( ○ )**

## 3. 검증 절차 (단계별, 순서대로 수행)

각 단계를 통과해야 다음 단계로 진행합니다.

| 단계 | 검증 내용 | 통과 기준 |
|---|---|---|
| **1** | 노드 간 SSH 무암호 접속 (master↔n1↔n3 전 조합) | 즉시 접속 성공 |
| **2** | 노드 간 L3 도달성 및 대역폭 (`iperf3`/`ib_write_bw`) | §2-1 판정 기준 참조 |
| **3** | 3노드 버전 정합성 (`nvidia-smi`/CUDA/NCCL/PyTorch) | 3노드 출력 완전 동일 |
| **4** | 노드 **내** 8-GPU all_reduce (`nccl-tests`) | busbw ≥ NVLink 규격의 70% |
| **5** | 2노드 **16-GPU** all_reduce | busbw ≥ 인터커넥트 규격의 70% |
| **6** | 3노드 **24-GPU** all_reduce | 16-GPU 대비 성능 저하 없음 |
| **7** | 24-GPU 실제 학습 잡 30분 연속 구동 | hang·NaN 없이 step time 일정 |

**4~6단계 명령 예시**

```bash
git clone https://github.com/NVIDIA/nccl-tests && cd nccl-tests
make MPI=1 MPI_HOME=/usr/lib/x86_64-linux-gnu/openmpi CUDA_HOME=/usr/local/cuda

# 24-GPU all_reduce
mpirun -np 24 -H master:8,n1:8,n3:8 \
  -x NCCL_DEBUG=INFO -x NCCL_SOCKET_IFNAME=<데이터망 IF> -x NCCL_IB_DISABLE=0 \
  --mca btl_tcp_if_include <데이터망 IF> \
  ./build/all_reduce_perf -b 8 -e 8G -f 2 -g 1
```

**PyTorch 24-GPU 학습 실행 형태**

```bash
# 각 노드에서 NODE_RANK만 변경하여 실행 (master=0, n1=1, n3=2)
torchrun --nnodes=3 --nproc_per_node=8 --node_rank=$NODE_RANK \
         --rdzv_backend=c10d --rdzv_endpoint=master:29500 \
         train.py
```

## 4. 인터커넥트가 저속(10GbE 이하)으로 확인될 경우의 대안

인터커넥트 증설이 단기간 불가능한 경우, **통신량을 줄이는 방향**으로 24-GPU를 활용할 수 있습니다.

| 전략 | 내용 | 노드 간 통신량 | 적용성 |
|---|---|---|---|
| ZeRO-1 + gradient accumulation | 통신 빈도 자체를 축소 | 낮음 | 높음 |
| 파이프라인 병렬(PP)을 노드 간 배치 | 노드 간에는 activation만 전달, all-reduce는 노드 내 | 매우 낮음 | 높음 |
| gradient compression / BF16 통신 | 통신 payload 축소 | 중간 | 중간 |
| **작업 병렬화(embarrassingly parallel)** | 노드별 독립 잡(하이퍼파라미터 탐색, 데이터 생성, RL 롤아웃) | **없음** | **매우 높음** |

> **즉시 적용 권고:** 마지막 항목(작업 병렬화)은 클러스터링 없이도 **24-GPU를 전부 가동**시킬 수 있는 방법입니다.
> 특히 강화학습의 **롤아웃(경험 수집)** 단계는 노드 간 통신이 거의 필요 없어, n1·n3를 롤아웃 워커로, master를 학습 노드로 배치하면 클러스터링 문제와 무관하게 가동률을 즉시 끌어올릴 수 있습니다.
> **9월 목표 가동률 55%는 이 방식을 전제로 산정한 수치입니다.**

## 6. 모니터링 지표에 대한 의견 (운영기관 협의 요청)

`nvidia-smi`의 `utilization.gpu`는 **직전 샘플링 구간에 커널이 1개 이상 실행되었는지 여부**를 나타내는 지표로, 다음 한계가 있습니다.

- GPU의 **연산 밀도**를 나타내지 않습니다. 전체 SM 중 1개만 사용해도 100%로 계측됩니다.
- 반대로, GPU가 작업에 **배타적으로 할당**되어 있어도 데이터 대기·통신 대기 구간에서는 0%로 계측됩니다.
- 분산학습에서는 all-reduce 통신 대기가 필연적이므로, 규모가 커질수록 Utilization은 구조적으로 하락합니다.

따라서 활용도 평가 시 아래 지표의 **병행 반영**을 요청드립니다.

| 지표 | 수집 방법 | 의미 |
|---|---|---|
| 자원 할당률(점유율) | 스케줄러 로그 (Slurm `sacct` 등) | GPU가 실제 작업에 배정된 시간 비율 — **활용 의지의 직접 지표** |
| SM Occupancy | DCGM `DCGM_FI_PROF_SM_OCCUPANCY` | 연산 밀도 |
| Tensor Core 활용률 | DCGM `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` | 실질 학습 연산량 |
| GPU 메모리 점유율 | `memory.used / memory.total` | 자원 점유 실태 |
| 평균 전력 | `power.draw / power.limit` | 실부하 수준 |

## 7. 결론

1. 본 시스템의 저활용은 **24-GPU 멀티노드 클러스터링 미구성이라는 단일 병목**에 대부분 기인합니다.
2. 해당 병목의 최우선 확인 대상은 **노드 간 인터커넥트(RDMA) 가용 여부**이며, 이는 자체 해결이 어려울 수 있어 운영기관 기술지원이 필요합니다.
3. 클러스터링 해소 이전에도 **독립 잡 병렬 투입(특히 RL 롤아웃)** 으로 24-GPU를 즉시 가동할 수 있으며, 9월부터 이를 적용합니다.
4. 병목 해소 시 11월 이후 목표 가동률 80~85% 달성이 가능할 것으로 판단합니다.
